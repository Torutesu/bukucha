# Bukucha SEO・GEO・LLMO 実行戦略

作成日: 2026-09-08 / 対象: 日本語Web版 / 初回監査の基点: `origin/main` の `205a708`

## 1. 90日でつくる状態

**女性向けのオリジナル恋愛小説を、シチュエーションから選び、AIと続きをつくれるサービスとして理解されること。その検索流入を、実際に物語を読み進める読者と作品を公開する作者につなげる。**

SEOは検索での発見、GEOは生成AI検索からの引用・送客、LLMOはAIがBukuchaの機能と制約を正しく説明できる状態として扱う。実装は共通の公開ページ・正確な説明・内部リンクを土台にする。AIごとの説明を大量に複製する施策は行わない。

90日間の主な成果物は、検索に取得可能な公開作品ページ、少数の実体験に基づくガイド、検索とAI経由の読者体験を測る仕組み、毎週改善できる記録である。順位・検索数・引用率・CV増加の実績は未取得。以下の検索意図と優先度は、現状の製品との適合性から決めた仮説であり、検索ボリューム調査済みの数値ではない。

Googleは、AI検索への掲載にも基本的なSEOとインデックス可能性が重要であり、専用の構造化データやAI向けテキストファイルを必須としていない。`llms.txt`の追加自体を成果指標にしない。[Google: AI features and your website](https://developers.google.com/search/docs/appearance/ai-features)

## 2. 誰に、何を約束するか

| 対象 | 解決すること | 公開説明で優先する表現 | 到達点 |
|---|---|---|---|
| 読者 | 好みの関係性・展開から恋愛小説を選び、自分の言葉で続きを変えたい | 女性向け、ノベル型AIチャット、シチュエーションから選ぶ、オリジナル作品 | 作品詳細 → 読み始める → 最初の応答成功 |
| 作者 | 好きな設定はあるが、最初からすべて書くのは難しい | 一文から下書き、キャラクター・導入を編集、公開前の確認 | 作成ガイド → 下書き → 編集 → 公開成功 |
| 比較検討中の人 | AIチャット・小説投稿・乙女ゲームの違いと、利用条件を知りたい | 体験の違い、対応機能、利用制限、公開範囲を具体的に説明 | サービス説明 → 試し読み |

PRD上の主対象は日本の10〜30代女性、夢小説・乙女ゲーム・TL/BL文化に親しむ層。ただし「夢小説」は既存IPの二次創作を探す意図も含むため、主訴求は**オリジナル恋愛小説**に寄せる。「既存作品のキャラクターと話せる」と誤解させる誘導をしない。

現行コードでは、匿名の利用者に表示できる作品は `PUBLISHED` かつ `ALL_AGES`。`R15`は18歳以上の判定とフィルター解除があるユーザーに限定される。ラベルから「15歳から利用できる」と推測して書かず、年齢表現は運営方針と実装を合わせて確定する。

料金、無制限利用、実AIの本番稼働、iOS/Androidアプリの配信、創作者への金銭報酬は、公開環境の確認が済むまで訴求しない。READMEの「無限に続く」は利用枠が無制限という意味には使わない。

`/search?q=...&tags=...&sort=...`の組み合わせを索引に増やさない。検索UIは探索機能として保ち、特定テーマへの需要と十分な作品が確認できたときだけ、説明と編集理由を備えた独立ページを追加する。公開作品が少ないテーマで、タグ名だけ変えたページを量産しない。

## 5. 公開する内容の品質基準

1. 冒頭で一つの質問に答える。例えば「ノベル型AIチャットとは」を短く定義してから、実際の使い方へ進む。
2. 一般論だけで終わらせず、Bukuchaで再現できるオリジナルの入力例、編集の理由、完成した公開紹介を載せる。会話ログや私的な設定を転載しない。
3. 実装済み・設定次第・未提供を分ける。料金、回数、年齢、公開範囲、対応端末の変更時は本文も更新する。
4. 執筆者・レビュー担当は実際に関与した人だけを記す。架空の「編集部」、経歴、専門家監修、評判を追加しない。作者の公開表示名は本人が公開した範囲で利用する。
5. 公開・更新日は実際の内容変更に対応させる。sitemapの`lastmod`を毎回現在時刻にして新しさを演出しない。
6. 見出し、表、箇条書きは読者が判断するために使う。FAQは実際の疑問に答える本文として用意し、構造化データだけに回答を埋めない。
7. 次の行動へつなぐ。読者ガイドから公開作品、作者ガイドから作成画面へ。関連ガイドとサービス説明へ戻れるリンクを置く。
8. すべての公開用文章は人が読み、機能・表現・オリジナル性を確認する。AI生成の下書きを使う場合も、編集確認を省略しない。

Googleは価値を加えない大量の生成コンテンツを問題とし、正確さ・品質・関連性と制作背景の説明を重視している。このため本計画では記事本数より「実例を試せる」「条件が正しい」「次の行動ができる」を受け入れ基準とする。[Google: 生成AIコンテンツのガイダンス](https://developers.google.com/search/docs/fundamentals/using-gen-ai-content)

構造化データはページの内容を表現する。ホームは`WebSite`、作品は適切な`CreativeWork`、案内ページは`WebPage`や`Article`など、確認できる実体だけを使う。表示していない運営法人・架空レビュー・価格・著者資格は出さない。構文が正しくても、リッチリザルトや引用は保証されない。[Google: 構造化データの一般ガイドライン](https://developers.google.com/search/docs/appearance/structured-data/sd-policies)

Googleの公式記録ではFAQリッチリザルトは2026-05-07以降表示されていない。FAQ本文の有用性と、検索結果の拡張表示は区別する。[Google: Search Consoleのデータ注記](https://support.google.com/webmasters/answer/6211453?hl=en)

## 6. 検索・AIへの公開範囲

| 対象 | 方針 | 確認方法 |
|---|---|---|
| ホーム・サービス説明・ガイド | 公開。canonicalと内容を統一 | HTTP本文、Google URL検査、リンク確認 |
| 全年齢・公開済み作品の紹介 | 公開対象。作者の公開紹介と導入だけを使用 | 匿名アクセス、公開状態変更後の再取得 |
| 下書き・非公開・停止作品 | sitemap除外。匿名に内容を出さない | IDを直接指定したHTTP/API確認 |
| R15等の制限作品 | 今回の公開検索対象に含めない | sitemap、metadata、OG画像、API、クライアントへのpropsを確認 |
| 個人の物語・会話ログ・本棚・マイページ・作成・設定・ログイン | noindex。機密情報はサーバーでアクセス制御 | 別ユーザー・ログアウト状態で本文とレスポンスを確認 |
| Googlebot / Bingbot / OAI-SearchBot | 公開ページを取得できる状態を維持 | robotsに加えてCDN/WAFの応答も確認 |
| モデル学習用クローラー | 検索掲載とは別の意思決定として扱う | 運営方針と各社の最新仕様を記録 |

OpenAIの検索用`OAI-SearchBot`と学習用`GPTBot`の設定は独立している。`ChatGPT-User`はユーザー起点の取得であり、検索への掲載を決めるbotではない。検索対策を理由に、非公開領域や学習利用まで一括で許可する必要はない。[OpenAI: Crawlers](https://developers.openai.com/api/docs/bots)

Google Search Consoleには「Search generative AI」のInclude/Exclude/親設定継承がある。**robotsの確認に加え、対象プロパティの設定と親からの継承を確認する。** Googleによると2026-08-31に全世界展開済みで、学習制御とは別の設定である。[Google: Search generative AI control](https://support.google.com/webmasters/answer/16908024)

将来R18を導入する場合は、今回の全年齢ページに自動で混ぜない。Googleは明示的コンテンツの分類について専用の指針を提供している。導入時にドメイン構成、年齢条件、metadata、画像とリンクの扱いを別途再設計する。[Google: explicit content guidelines](https://developers.google.com/search/docs/specialty/explicit/guidelines)

初月の編集枠は、サービス説明と3本の基礎ガイドの検証を優先する。翌月は「恋愛シチュエーションを組み立てる」「導入を編集して物語を始めやすくする」など、既存ガイドにない実例を最大4本程度の制作枠で検討する。本数は作業計画であり、成果予測や公開義務ではない。

作者インタビュー・利用事例・他サイトへの情報提供は、実際の協力者と掲載同意が得られてから行う。送信・勧誘・外部投稿はこの文書を作成しただけでは実施済みとしない。被リンク購入や自作の第三者推薦を行わず、読者が使える公開例や制作ノウハウを育てる。

## 8. Search Console / Bingの立ち上げ手順

1. 本番originと所有者を確定する。独自ドメインの場合はDNSで管理できるプロパティを、Vercel共有ドメインの場合は対象URLの所有確認方法を選ぶ。未確認のverification tokenをコードに書かない。
2. 所有確認後、正規originの`/sitemap.xml`を送信する。登録対象は正規URLで取得可能な公開ページだけ。送信成功とインデックス登録は別々に記録する。
3. ホーム、ガイド1本、全年齢の公開作品1本をURL検査する。robots、取得HTML、canonical、インデックス状態を保存する。リリース直後の重要URLだけ、必要に応じて登録をリクエストする。
4. GoogleのSearch generative AI設定のInclude/親継承を確認する。変更日、対象プロパティ、変更前後を記録する。
5. GSCの通常検索とGenerative AI performance、BingのSearch PerformanceとAI Performanceを別々に保存する。権限がなければ「未接続」、レポートが出なければ「利用不可/表示母数不足」と記録する。
6. robotsと公開URLを検索botのUAでも取得し、WAF・認証・JavaScript challengeで遮断していないか確認する。UAだけの偽装は本物のbot来訪証拠にはしない。
7. 週次でページ索引、sitemap取得エラー、5xx、canonical不一致を確認する。作品が非公開・削除になった際はsitemapから除外し、公開紹介が取得できないことを確認する。

Search Consoleは索引状況・検索パフォーマンス・構造化データ等の確認に使う。[Google: Search Console概要](https://support.google.com/webmasters/answer/9128668)

**2026年9月時点の測定仕様:** GoogleはGenerative AI performanceレポートを提供し、AI Overviews/AI Modeの表示回数をページ・国・デバイス・日付で確認できる。通常のWeb検索レポートにも含まれるので、両者の数字を足さない。表示回数の専用レポートを、AI経由クリック/CVの完全な内訳として扱わない。[Google: 公式発表](https://developers.google.com/search/blog/2026/06/gen-ai-performance-reports)、[レポート仕様](https://support.google.com/webmasters/answer/16984139)

Bing AI Performanceは対応するMicrosoftのAI体験等における引用を扱い、引用URLと推移を確認できる。2026年6月にはIntents/Topics/Citation Share/Compareが追加された。これを全AIサービスでの引用率や検索順位と読み替えない。[Bing: AI Performance](https://blogs.bing.com/webmaster/February-2026/Introducing-AI-Performance-in-Bing-Webmaster-Tools-Public-Preview)、[Bing: 2026年6月の拡張](https://blogs.bing.com/search/June-2026/New-AI-Visibility-Insights-in-Bing-Webmaster-Tools-Intents-Topics-Citation-Share-Compare)

## 9. プライバシーを守るCV計測の設計

この節は実装仕様案。計測基盤・保存期間・同意方針は未確定であり、この作業で計測が稼働したという意味ではない。恋愛の好みや会話内容が日常の分析に出ないことを要件にする。

| イベント案 | 成功の定義 | 許可する値の例 | 禁止する値 |
|---|---|---|---|
| `public_landing` | 公開ページに到着 | `page_type=home/guide/situation`、固定のガイドslug、許可したsource区分 | 完全なreferrer/URL、検索文、タグ選択、ユーザーID |
| `reader_start` | 読書を開始する操作が成立 | `entry_type=guide/home/situation` | 物語ID、個人ペルソナ、作品名、本文 |
| `first_reply_success` | 最初のAI応答が正常に完了 | `mode=guest/member`、source区分 | 入出力、メール、生年月日、作者/読者ID |
| `draft_created` | サーバーで下書き作成に成功 | `entry_type`、成功/失敗区分 | 妄想の入力、設定文、下書きID |
| `situation_published` | サーバーで`PUBLISHED`へ変更成功 | 固定の入口区分、成功区分 | 非公開の設定、moderation詳細、ユーザーID |

CVの主指標は読者の`first_reply_success`と作者の`situation_published`。CTAクリックは途中の指標として分ける。LLMの失敗・レート制限・登録失敗を、体験成功として数えない。

実装時はイベントとパラメータをallowlistで検証し、公開ページの種類に正規化する。`/story/[id]`などの生のURLをanalyticsへ送らない。自動のpage view・site search・フォーム計測・セッション録画は、必要性と送信内容を確認せず有効にしない。GoogleもURL/title、検索欄、フォーム、イベントに個人情報が混ざるリスクを明記している。[Google Analytics: PII送信を避ける](https://support.google.com/analytics/answer/6366371)

流入元は、許可した参照元ホストを`google/bing/chatgpt/perplexity/other/direct_unknown`に分類し、生のreferrerは破棄する案を基本とする。任意のUTM文字列を保存せず、運営が決めた固定値だけ受け付ける。参照元がない来訪をAI経由と推測しない。

同一タブ・短時間の転換を測る場合は、30分などの有効期間を持つ一時的なランダム識別子と入口区分だけを用いる設計を検討する。アカウント・会話・端末指紋との結合はしない。保存期間は暫定案としてイベント30日、集計90日とし、運営が確定した方針を実装とプライバシー説明へ反映する。これは現在の保存期間を表すものではない。

広告連携・クロスデバイス追跡・ユーザー別嗜好分析は初期計測の範囲に入れない。少数の組み合わせを日報で見せず、集計対象10件未満をまとめる等の基準も検討する。集計だけでも取扱いの説明は必要であり、「匿名なので何でも取得できる」としない。

## 10. AI回答の固定検証

毎週同じ曜日を目安に、日本語・日本地域・新しい会話・Web検索を有効にした条件をできるだけ揃えて確認する。利用可能なGoogle AI機能、ChatGPT検索、Bing/Copilotなどを分け、サービス名・日時・表示モデル・検索の有無を記録する。アカウント差や回答の揺れを前提に、単発の結果を市場全体の引用率としない。

| ID | 固定質問 | 確認すること |
|---|---|---|
| B01 | Bukuchaとはどんなサービスですか。公式情報を出典に説明してください。 | 名称、女性向け、オリジナル、読む/書くの説明と公式URL |
| B02 | Bukuchaは無料で無制限に使えますか。現在の利用条件を確認してください。 | 確認できない料金/無制限を断定しない |
| B03 | Bukuchaでは既存アニメのキャラクターを使った作品を公開できますか。 | オリジナル限定の方針を正しく説明 |
| B04 | Bukuchaで作った作品の公開範囲と、私が読んだ会話の公開範囲を教えてください。 | 公開紹介と私的会話を混同しない |
| N01 | 女性向けのオリジナル恋愛小説をAIと一緒に読み進めたいです。選び方を教えてください。 | 非指名の選択肢への出現、紹介の適合性 |
| N02 | キャラクターと会話する形式より、地の文のある物語を楽しめるAIサービスを探しています。 | ノベル型の違いを説明できるか |
| N03 | 幼なじみとの恋愛を題材に、オリジナルのシチュエーションを一文から作る方法を教えてください。 | 作者ガイドへの引用・関連性 |
| N04 | AI小説でキャラクターの関係性と最初の場面を決めるコツを教えてください。 | 実例のあるガイドが回答に使われるか |
| N05 | AI恋愛小説を読むとき、プライバシーと公開範囲は何を確認すればよいですか。 | 正確なサービス条件を根拠つきで示せるか |
| W01 | 実在する公開作品のタイトルを指定して、設定と作者の公開表示名を教えてください。 | 公開作品だけを引用し、私的設定を出さない |

W01は公開を確認した作品名に置き換え、固定後は同じ作品で追跡する。作品が非公開になれば、その日を記録して検証セットを更新する。ユーザーの私的な物語は入力しない。

各実行で「名前への言及」「Bukucha公式URLへの引用」「記述の正誤」「引用URLが取得可能か」を別々に記録する。引用率は、**この固定セット内の公式引用あり回答数 ÷ 検証を完了した回答数**としてのみ表示する。名前の言及率やBing Citation Shareとは別指標。全体で10質問なら分母10を必ず併記し、未実行を0として混ぜない。

記録項目:

```text
実施日 / サービス / 言語・地域 / 検索の有無 / 表示モデル
質問ID / 実際の質問 / 回答の短い記録 / 言及の有無
公式引用の有無 / 引用先URL / 誤説明 / 想定する出典ページ
次の修正 / 修正日 / 次回の結果
```

誤説明があれば、まず公式ページの不足・曖昧さ・矛盾を修正する。AIに有利な回答を強制する隠し文や、クローラー専用の異なる説明を追加しない。

## 11. 週次KPIと判断ルール

開始2週間は基準値の取得期間。以下の「0件」「100%」は制御可能な品質基準であり、流入や順位の予測ではない。

| 領域 | 記録する値 | 判断と次の行動 |
|---|---|---|
| 公開品質 | 代表URLの取得成功、canonical一致、本文有無、漏えい/不適切掲載件数 | 対象テンプレートの確認完了100%、非公開情報の露出0。失敗は最優先修正 |
| 索引 | sitemap掲載数、索引済み数、除外理由、URL検査日 | 索引率100%を要求せず、代表ページの除外理由を確認。重複・薄い内容・取得障害を分ける |
| 通常検索 | 指名/非指名のimpressions・clicks・CTR、主要ランディングページ | 直近28日と前28日を同条件で比較。母数とクエリの変化を併記 |
| Google AI検索 | Generative AI performanceのimpressionsと対象ページ数 | 通常検索と重複するため加算しない。未表示のレポートはN/A |
| Bing AI検索 | 引用数、引用ページ、利用できればCitation Share/Topics | 対応面の数値として比較。検索順位やChatGPT全体の成果に置換しない |
| 読者CV | 最初の応答成功数、成功数/計測対象の公開到着セッション数 | クリックだけ伸びて成功が増えない場合は読み始める導線・失敗率を確認 |
| 作者CV | 下書き成功数、公開成功数、下書き→公開率 | 投稿量だけを成果にせず、公開品質と完遂率を確認 |
| AI記述品質 | 固定セットの公式引用件数/検証数、事実誤り件数 | 誤りのある条件説明を修正。数回の変動で記事を大量追加しない |
| 編集 | 実操作確認済みガイド数、改訂数、孤立ページ数 | 新規制作と改訂の理由を保存し、孤立した公開ページをなくす |

通常検索ではGSCに表示されない少数クエリもある。クエリ行の合計を全体値と同一視しない。CVは同意・計測できた範囲の値であり、全利用者の完全な転換率とはしない。

運用の目安として、同一ページ/同一意図で十分な表示回数が溜まったらtitleと説明文を確認する。例えば28日で100impressions未満なら、CTRの微差で採否を決めず、取得・意図・内部リンクを優先する。100は統計的有意性を保証する基準ではなく、少数データの過剰解釈を避ける作業上の目安である。

週次レビューは「何が変わったか」「どの証拠か」「翌週一つ何を変えるか」を残す。流入が少なくても、認証・公開範囲・誤説明の問題は継続して解消する。
